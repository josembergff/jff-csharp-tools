# ADR-001 — Adopting a Multi-Target, Layered Library Architecture for jff-csharp-tools

| Field        | Value                          |
|--------------|--------------------------------|
| **Status**   | Accepted                       |
| **Date**     | 2024-01-01                     |
| **Author**   | Josemberg Farias Ferreira      |

---

## Context

The goal of `jff-csharp-tools` is to provide a reusable, opinionated set of utilities for .NET Core
applications. The key challenges were:

1. **Multi-version .NET support** — Consumers run different LTS and STS versions of .NET (6, 8, 9).
   A single target would force all consumers to upgrade or stay on a specific version.
2. **Shared core vs. framework-specific code** — Domain models, entities, filters, and extension
   helpers are pure C# and do not depend on any specific runtime. However, repository, service,
   controller, and HTTP-pipeline components do require framework-specific APIs.
3. **Separation of concerns** — Mixing domain logic with presentation or infrastructure code would
   make the library harder to consume partially and harder to test.
4. **Reusable CRUD scaffolding** — .NET API projects consistently need the same boilerplate: base
   entities with audit fields, generic repository and service layers, standard CRUD controllers,
   global exception handling, and JWT-based authentication helpers.

---

## Decision

### 1. Multi-target NuGet packages split by .NET version

Three separate NuGet packages are published:

| Package                  | Target Framework    | Purpose                                              |
|--------------------------|---------------------|------------------------------------------------------|
| `jff_csharp-tools`       | netstandard2.1      | Shared core: entities, models, filters, extensions   |
| `jff_csharp-tools-6`     | net6.0              | Repository, Service, Controllers, Filters for .NET 6 |
| `jff_csharp-tools-8`     | net8.0              | Same as -6, compiled for .NET 8 with updated deps    |
| `jff_csharp-tools-9`     | net9.0              | Same as -8 + Minimal API helpers, Guid variants      |

The versioned packages (`-6`, `-8`, `-9`) each hold a **project reference** to the core library,
so consumers install a single package and get everything they need.

### 2. Layered internal architecture (Domain + Presentation)

Each versioned package follows a two-layer structure:

```
Domain/
  Entity/          — DefaultEntity<T>, DefaultGuidEntity<T>, LogSerilogEntity
  Interface/
    Repository/    — IDefaultRepository<T>, IDefaultGuidRepository<T>
    Service/       — IDefaultService<T>, IDefaultGuidService<T>
  Repository/      — DefaultRepository<T>, DefaultGuidRepository<T>
  Service/         — DefaultService<T>, DefaultGuidService<T>

Apresentation/
  Controllers/     — DefaultController, DefaultCRUDController, DefaultGuidCRUDController
  Endpoints/       — CrudEndpoints, CrudGuidEndpoints  (v9 only)
  Filters/         — ExceptionFilter, TokenEnumFilter, UnitOfWorkFilter
  Extensions/      — HttpContextExtension, DefaultResponseModelExtension
  Configs/         — EnumConverter
  Attributes/      — AttributeEnum
```

### 3. Repository pattern with EF Core

All database access is encapsulated behind `IDefaultRepository<T>` / `IDefaultGuidRepository<T>`.
`DefaultRepository<T>` is the EF Core implementation. This allows consumer apps to swap the
underlying storage without changing service or controller code.

### 4. Generic base entity with audit fields

All entities extend `DefaultEntity<TEntity>` (int user id) or `DefaultGuidEntity<TEntity>`
(Guid user id), which enforces:
- `Id` (int primary key)
- `CreatorUserId` (int or Guid — links every record to its creating user)
- `CreatedAt` / `UpdatedAt` (audit timestamps)
- `GetFilter()` — self-describing LINQ filter expression

### 5. JWT-based user identification

`DefaultController` extracts the current user's ID from a JWT Bearer token claim
(`CurrentIdUser_FromBearerToken`). All service operations accept this `IdUser` parameter for
row-level security: users can only read/update/delete their own records by default
(`filterCurrentUser = true`). This can be disabled per-endpoint when needed.

### 6. `DefaultResponseModel<T>` as a universal response envelope

All service methods return `DefaultResponseModel<T>`, which unifies:
- `Result` — the operation result
- `StatusCode` — HTTP status
- `Error` / `Message` / `MessageList` — error and info messages
- `Success` — computed flag

This ensures consistent HTTP responses across all controllers and Minimal API endpoints.

### 7. Minimal API support (v9 only)

`CrudEndpoints.MapCrud<TEntity, TContext>()` allows registering all CRUD routes with a single line
in `Program.cs`, supporting the modern Minimal API style introduced in .NET 6 and refined in .NET 9.

---

## Consequences

### Positive

- Consumers on any supported .NET version get a stable, matching package.
- The layered design keeps domain logic independent of the HTTP framework.
- Generic base classes eliminate repetitive CRUD boilerplate in consumer projects.
- Row-level security is built in by default via `CreatorUserId` filtering.
- Centralized `ExceptionFilter` standardizes error responses without repetition.

### Negative / Trade-offs

- Three separate packages increase maintenance overhead when shared logic changes.
- The `netstandard2.1` core library cannot use newer C# / .NET runtime features.
- Tight coupling to EF Core means consumers must use EF Core; no alternative ORM is supported
  out of the box.
- The opinionated base entity requires `int` or `Guid` primary keys; other key types need
  custom implementations.
